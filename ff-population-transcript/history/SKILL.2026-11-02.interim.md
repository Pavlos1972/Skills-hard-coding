## Client File Access (standing rule — applies to every step below that reads or saves a client file)

Every time this skill needs a client's document, or needs to save a newly produced deliverable into the client's folder, follow this exact order, every time, without asking first:

1. **Local machine — always attempted first.** Connect via the device bridge to Paul's local machine and check **both** of these locations under `liferisk.co.za` for the client's folder (same `[Business Segment]/[Surname], [First Name]/Fact Find` structure under each): `Company - Paul` (used for New Business, but not limited to it) and `Company - WR Clients` → `Paul Kafentzis (Client Files)` (used for current/existing clients). A given client's material could sit under either — check both and use whichever one actually has the file. This connection is expected to succeed and must be tried first, every time — never skip straight to asking Paul to attach something. If this session has no live device-bridge connection to Paul's computer yet, request it before doing anything else that depends on client files. **Laptop availability window: Paul's laptop is reachable ~8:45am on weekdays only; if the bridge is down outside that window, say so plainly rather than treating it as a failure.**
2. **SharePoint — only if the local machine genuinely can't be reached.** If, and only if, the device bridge cannot connect to Paul's computer this session, fall back to the identical two-location check via SharePoint. This should be rare — treat a failed local connection as the exception, not the default path. Be aware this path requires embedding the file's content as base64 text in one message when saving, which has a real practical ceiling — a large PDF may need lossless compression first (e.g. `qpdf --recompress-flate --object-streams=generate` followed by `gs -dPDFSETTINGS=/ebook`). Always visually re-verify a compressed PDF before treating it as the deliverable.
3. **Ask Paul to attach the file — last resort only.** Only once both the local machine and SharePoint have genuinely been tried and neither works does this skill ask Paul to upload the Audio to Text file, transcript or other source directly, or say plainly what's blocking the folder save.
4. **Never touch another broker's folder.** `Company - WR Clients` holds a separate `(Client Files)` folder for every broker at the firm. `Paul Kafentzis (Client Files)` is the only one under `Company - WR Clients` this skill ever reads from or writes to. This restriction does not apply to `Company - Paul`, which is Paul's own folder.

This applies to **locating the Audio to Text file, transcript and Overview** (Steps 1 and 1b below), to **checking the client's other documents for a field that can't otherwise be resolved** (Step 3 below), and to **saving every deliverable this skill chain produces** (Step 5a below) — same order, every time.

## Out of scope: no transcript, but a Fact Find already exists

If the client already has a **completed** Fact Find document and there is **no accompanying meeting transcript** to populate from, this skill does not apply. Go straight to the `fact-find-summary` skill against the existing completed FF instead. That skill has its own rule for this exact case: it still produces the summary PDF, but the Planner note (always made by `client-teams-transcript-skill`'s program and presented as its copy-ready page, per Step 7b below) can't be produced with no transcript to summarize — say so explicitly rather than silently omitting it.

## Step 1: Gather inputs (source order — rule 11)

Gather in this order, per the Client File Access order above:

1. **The Fact Find form's data file (named `Fact Find (Audio to Text)`)** — see Step 1b. This is the first and primary source.
2. **The transcript(s)** — usually `.docx`, sometimes text despite the extension. The file is named `Teams meeting transcript - DD.MM.YY - (Client Name)_ Annual Review [year]` (or `... - FF`, or with another suffix) — search the client's `2. Fact Find` folder for the meeting date and client name; identify by content, not only by name (rule 10).
3. **The client's latest Overview** in the `1. Overview` folder (see Step 1b). Reference only.
4. **The Manual Fact Find — only if the Audio to Text file is absent** (see Step 1b).

If the Audio to Text file and the transcript are both missing after checking the client's folder, ask for them — unless a completed FF already exists with no transcript (see Out of scope).

- **Multiple transcripts for one meeting:** if the client's Teams call dropped and reconnected, there will be two (or more) transcript files for the same date. Read all of them and treat them as one continuous meeting.
  - **Verify continuity before summarizing anything.** Check that the last exchange of transcript N and the opening exchange of transcript N+1 pick up the same topic/figure. If there's a real gap, flag it rather than silently filling it in.

## Step 1b: The Fact Find (Audio to Text) file, the Overview, and the Manual Fact Find as last resort

**A. The Audio to Text file — first and primary source (Paul's rule, 28/10/2026).**
1. **Locate it - by content as well as name.** Paul's new Fact Find form saves a data file (`.json`) and a PDF. The name stays as it always was (Paul, 02/11/2026: keep "Audio to Text"): `Fact Find (Audio to Text) - DD.MM.YYYY - [Name Surname].json` plus the same name as `.pdf`, in the client's `2. Fact Find` folder (both locations per the Client File Access order). The form's own test files may be called `Fact Find - DD.MM.YYYY - [Name Surname].json`, and a `Fact Find (Voice to Text)` name may appear, so list the whole folder, open the candidates, and recognise the data file by what is inside it (`app` is `wr-fact-find`), not by its name. Use the one dated the meeting date for this client.
2. **Read both the JSON and the PDF.** The JSON is the first source: every field sits under `f` as a value `v` with a status `st` (`confirmed`, `preset` or `empty`; files from the older form also use `heard` and `verify`), and the repeating lists (risk policies, retirement funding, debts, children and so on) sit under `l` as rows. The PDF is the readable copy of the same Fact Find (WR Fact Find v3.0). Extract both programmatically AND render the PDF pages and look at them. If the PDF and the JSON disagree on a field, flag it and quote both. The form's own area summaries (`sum`) and drafted action list (`pa`, `pa_actions`) are not sources: the facts come from the fields and lists, and the actions for Sitamah come from the Planner note (Step 7b).
3. **Use everything that is populated, whatever its status.** `confirmed` and `preset` values (and `heard` and `verify` values in an older file) are all populated values and all go into the Fact Find. A field counts as unanswered only when it is `empty` (or blank/"None recorded" in the PDF). Template defaults left in place by the form are `preset` values: use them, but check them against the transcript like everything else.
4. **The Audio to Text file wins; the difference is flagged.** Where the transcript/recording differs from the Audio to Text file, write the Audio to Text value and add a flag quoting both values and where each came from (for example: "Highest education: Audio to Text file says 3-year degree; on the call the client said a one-year diploma"). Never silently pick the transcript's value, and never silently drop the difference. Two things are exceptions because Paul set them as standing rules: the standing ABIs and the Dread Disease default (Step 3), and the policy number, which is always taken from the actual policy schedule (Step 3). Each exception is mentioned in one line when it changes an Audio to Text value.
5. **Gaps.** Where the Audio to Text file is blank, "None recorded" or `empty`, fill the gap from the transcript, then the Overview, then the client's other documents on file (Step 3). A value filled from the transcript is stated as fact if clear; unclear audio is flagged, not turned into a fact.
6. **Say what you did.** The source report (Step 5) states what the Audio to Text file contributed, with every `preset` entry (and every `heard` and `verify` entry in an older file) listed, as well as every difference found.
7. **Check the form's schema version every run (Paul, 02/11/2026).** Read `schema` at the top of the JSON. This skill knows `3.0`. If it says anything else (the form's code is changed from time to time), stop before building and tell Paul in one line which version you found; never guess how a new version lays out its fields.
8. **Do not process the parking list (Paul, 02/11/2026).** The JSON's `unplaced` list holds facts the form heard but did not place in a box. That is deliberate: only the crucial facts go into a field. The Teams call is recorded, so the transcript carries everything else; use the transcript for the extra context. Do not read `unplaced` as a source and do not list its entries.
9. **Use the saved value.** If a field in the file is wrong, Paul corrects it in the form himself and saves again. Never change a value because the transcript sounds different; flag the difference under point 4 as always.
10. **Check the company look-up text (Paul, 02/11/2026).** The form can look up on the web what a company does and write it into the 'what does the company do' field. Read that text before using it. Throw it out if it talks to the reader (for example "try again", "I found no...", a question) or is much longer than a short description (more than about 40 words), and replace it from what the client said in the transcript; if the transcript does not say, show `Not stated` and list it for Paul. A clean look-up that nobody confirmed is shown marked "web look-up, not confirmed with the client". If the file marks such a look-up `confirmed`, tell Paul in the hand-over message that the form's look-up should say "to verify", never "confirmed".

**B. The transcript — second, equally important source.** Read the whole transcript, start to finish, at least twice before drafting. It confirms, corrects (as a flag), and adds context to the Audio to Text file: reasons, plans, who pays what, timing. Extra context still goes in the relevant field or Notes even when the Audio to Text file already supplies the basic value.

**C. The client's latest Overview — reference.** Look in the client's `1. Overview` folder for the latest Overview (the one with the latest date in its name or modified date; the PDF and the spreadsheet both count). Use it to cross-check policies, policy numbers, premiums, cover amounts, escalation rates and group risk/retirement figures. It is a point of reference, not a primary source: it never overrides the Audio to Text file or the transcript silently. Differences are flagged. If there is no Overview, say so in the report and carry on.

**D. The Manual Fact Find — last resort, only if the Audio to Text file is absent.**
1. If, and only if, no Audio to Text file exists for this meeting (both locations checked, the whole folder listed, every candidate opened), look for the Manual Fact Find: Paul's filled-in copy of the WR Fact Find template, found **by content, not by file name** (`Fact Find (Manual) - [DD.MM.YY] - (Surname, First Name).pdf`, `Fact Find Template - [DD.MM.YY] - (Surname, First Name).pdf`, or similar). Open every candidate and check whether it carries entered values (form fields via pypdf, plus a rendered look). A WR Fact Find PDF with the client's name, ID, income, debts etc. filled in IS the Manual Fact Find, whatever it is called. A PDF with only template defaults ("N/A", "0.00", blank) is just the empty template. A name that does not match the expected pattern is never a reason to say it is missing.
2. Read it properly: extract form-field values AND render the pages and look at them. Tell the template defaults from real answers: a field counts as answered only when it carries a value Paul entered or a deliberate tick, or when the transcript corroborates it.
3. In that case the Manual Fact Find takes the place of the Audio to Text file as the primary source, with the same rule: where the transcript differs, the Manual Fact Find value is used and the difference flagged.
4. If neither the Audio to Text file nor a Manual Fact Find exists, continue from the transcript alone (and the Overview), say so plainly in the report, and invite Paul to point to the file if it is somewhere else. Never claim a source was consulted when it was not found, and never claim it was not found when a candidate was left unopened. **Named precedent:** [client C], 12.10.26 - the Manual FF was saved as `Fact Find Template - 12.10.26 - (Surname, First Name).pdf`; it was staged but never opened and the draft said none existed.

## Step 1d: Two spouses in one meeting (Paul's rule, 15/10/2026)

When the meeting covered a couple (for example one Teams call with both spouses), treat them as two clients and run the whole chain twice, once per spouse:

1. **Separate sets.** Two Fact Find Transcript PDFs, two Fact Find Summary PDFs, two Planner note pages (one per spouse) and two Teams messages (one per spouse, each only after Paul's yes). File names use each spouse's own name: `Fact Find Transcript - DD.MM.YY - ([Name Surname]).pdf`, and the same pattern for the Summary.
2. **Each spouse's own folder.** Save each spouse's PDFs into that spouse's own `2. Fact Find` folder (both locations per Client File Access). Use the folder's real spelling, even where it differs from the spelling in the recording or the file names, and mention the difference to Paul in the hand-over. Never save one spouse's reports into the other's folder.
3. **Never mix the spouses' information.** Occupation, income, policies, health, retirement, investments, medical aid, will and personal needs belong only to the spouse they were stated about. **Only two things are common to both and appear in both sets: the debts and the children / childcare** (every debt and every child, in full, in both).
4. **Joint policies** (one policy covering both spouses) appear in both sets, labelled joint, with the other spouse named. A policy on one spouse alone appears only in that spouse's set.
5. **Speaker labels.** The recording may label both spouses with the same name. Attribute every statement from its content (who owns the policy, whose job, "my husband / my wife") and from the Audio to Text file(s), never from the label. Where a statement cannot be attributed with evidence, do not guess: flag it in the notes of both sets and to Paul.
6. **The Audio to Text file.** There may be one Audio to Text file per spouse, or one for one spouse only. Use each file only for its own spouse (plus the common debts and children). For a spouse with no Audio to Text file, the transcript and that spouse's own documents are the sources; template defaults are not answers.
7. **Calculations.** Each spouse's own take-home income, minus the full childcare total, minus the full debt repayments (every debt, every child, in both sets) gives that spouse's Total Household Income Needed. If the result is negative, show the figure as calculated, do not adjust it, and flag it for Paul.
8. **Summary intro line.** Each Summary opens with one line saying it is a joint meeting with a spouse, covers this spouse only, and that debts and children are common to both.
9. **Cross-check before delivering.** Search each spouse's finished PDFs for the other spouse's income, policy numbers, premiums and personal facts. The only overlap allowed is the common debts, the children and the joint policies. Report the result in one line in the hand-over.
10. **Actions.** Write each Planner note's actions for that spouse, and list a shared action (for example a Letter of Authority for each spouse) in both notes.

## Step 2: Follow the Audio to Text file's own layout (v3.0)

The Fact Find Transcript follows the layout of the Audio to Text file (WR Fact Find v3.0, October 2026): the same sections, the same labels and the same order, in the same two-column style. Re-derive the structure from the real Audio to Text PDF of that client every run (it is the template), and do not force the document into any older layout. The v3.0 sections, in order, are:

1. **Client Info** — Meeting (consent to record and transcribe, advisor, date completed, type of meeting, referral from); Client (name, surname, date of birth, age, ID or passport, number, gender, nationality, income tax number); Contact details (cell, work, home, personal email, work email); Background (smoker, highest education, qualification details, notes).
2. **Occupation** — Work (employed, employer, what the company does, business owner, occupation, full time or contract, years in this occupation); Duties split (all the percentages, total); brief description of duties; notes. Business-owner fields only if Business owner = Yes.
3. **Income & Household** — gross monthly income, direct net income, take-home net income, monthly expenses / budget, disposable income, marital status, spouse/partner fields if any, notes.
4. **Existing Cover & Retirement** — personal risk cover (has cover, joint cover with spouse, group risk through employer); existing personal risk policies table (provider, spend, broker on record, notes); retirement funding table (type, provider/administrator, value, monthly contribution, broker on record); notes.
5. **Investments** — each investment, notes.
6. **Medical, Will & Short-Term** — medical aid (provider, plan, broker, notes); gap cover; will (has a will, up to date, held with, broker, last updated, notes); short-term insurance (has, broker, car, household contents, structural, business, spends, notes).
7. **Debts** — each debt (type, provider, description, owner, payer, term left, instalment, balance, asset value, credit life with lender, surety signed, notes); totals (monthly, liabilities, assets); notes.
8. **Children** — each child (name, surname, gender, date of birth, age, education stage, monthly cost); total childcare; notes.
9. **Health** — general health good, diabetes/high sugar, high cholesterol, high blood pressure, high BMI, other health issues, health notes.
10. **Advisor Actions** — Personal risk quotes (FNA quote with type and insurer; Shortfall quote with type and insurer; reduced quotes; preferred monthly spend; notes); Retirement & investment quotes (RGAR, retirement age, net amount; retirement annuity quotes; EGAR; investment quotes; notes); Referrals & documents (short-term (Cameron), medical & gap (Valerie), will (Capital Legacy), others; documents to request; notes).
11. **Risk Calculation** — Life cover: fractured cover; Life cover: standard; Permanent disability: fractured cover; Permanent disability: standard; Dread disease; Income protection / sickness benefit; notes.

## Step 3: Map the sources to fields — rules

- **Only fill in what is in a source** — the Audio to Text file, the transcript, the Overview or a client document.
- **How the sources combine (rule 11):**
  - The Audio to Text file is the base. Every populated value goes in, whatever its status.
  - The transcript fills every gap the Audio to Text file leaves (unclear, blank or `empty` fields), and adds the context (reasons, who pays what, timing, plans) to the relevant field or Notes.
  - Where both give the same answer, state it once, as fact.
  - Where they differ, the Audio to Text value is written and the difference flagged, quoting both values and where each came from, so Paul can decide. A difference only in spelling, format or level of detail is not a conflict - use the fuller/cleaner value and do not flag.
  - The Overview is cross-checked against both; differences are flagged, never silently resolved.
- **Never guess or invent a value.** Mark unanswered fields "N/A", "Not discussed", or "Requested" as appropriate.
- **"Not discussed" is a claim, not a default — verify it before writing it, against the Audio to Text file, the transcript and the Overview.** Re-search all three, and the client's other documents, before marking anything "Not discussed". **Named precedent:** [client D], 1 September 2026 — four debt fields were wrongly marked "Not discussed" when all four were answered on the call. **Named precedent:** [client B], 09.10.26 and [client C], 12.10.26 — drafts built from the transcript alone left fields open that Paul's own Fact Find record had already answered.
- **When a field can't be resolved from the Audio to Text file, the transcript or the Overview, check the client's other documents on file before marking it unconfirmed.** A policy schedule, servicing record, application, payslip, benefit statement or welcome pack can confirm a beneficiary nomination, a policy number, a tax number, contact details, or similar. **Named precedent:** [client A], 07.10.26 (review) — checking the BrightRock Owner's Manual already in the client's folder answered a beneficiary question Paul couldn't answer live: Estate [x]% / [beneficiary] [y]% (flagged only as pre-dating the client's March 2025 marriage).
- **The policy schedule (or the insurer's own equivalent current-policy document) is the ultimate source of truth for a policy number — never an Overview spreadsheet, a prior Fact Find, an Audio to Text entry or a quote/FNA reference number.** Resolve conflicts against the most recent genuine policy document and state the resolved number as fact, mentioning in one line that it differs from the Audio to Text file/Overview. Do not confuse a policy number with a quote/FNA reference number. **When the conflicting document is itself one Claude can correct** (e.g. the WR Overview spreadsheet), correct it directly — see Step 5a. **Named precedent:** [client A], 07.10.26 (review) — the WR Overview spreadsheet recorded [policy no. B]; the Owner's Manual and Change Moment Pay-out Guide (both dated 11.07.24) agreed on [policy no. A]. Corrected in the Fact Find and in the spreadsheet itself.
- **For any other value where a source document disagrees with the Audio to Text file** (for example a benefit statement showing a different fund value), the Audio to Text value is written under rule 11 and the document's figure is flagged prominently with both values, so Paul decides. Never silently use the document's figure and never leave the difference unflagged.
- **An FNA, Shortfall, or Reduced quote request must state two things explicitly, everywhere it is written: (1) WHICH INSURER the quote is to be requested from, and (2) whether it is Servicing or New Business — never left as just "a new FNA/quote".** **Servicing** — the insurer makes the quoting changes inside the client's existing policy; **New Business** — a fresh quote that would create a *second, separate* policy. **There is no default (Paul, 15/10/2026: "no servicing whatsoever"). Never assume Servicing because the client already holds a policy with that insurer, and never assume the insurer.** Take both from the Audio to Text file's quote fields (type of quote and insurer) and from what Paul said on the recording. **If neither source says which insurer to request the FNA / Shortfall / Reduced quote(s) from (or whether it is New Business or Servicing), ASK Paul before the Fact Find is finalised** (AskUserQuestion, or a plain-text question if unattended: "Which insurer should the FNA, Shortfall or Reduced quote(s) be requested from, and is it New Business or Servicing?"). If the recording is unclear on the insurer even though the Audio to Text file states it, use the Audio to Text value and flag the unclear recording. Applies equally to an FNA, a Shortfall quote (Group Risk), and a Reduced quote. **Named precedents:** [client A], 07.10.26 (review) — Paul specified a BrightRock Servicing FNA against the existing policy ([policy no. A]), not a New Business quote. [clients F and G], 14.10.26 (spouses, one meeting) — the first draft defaulted to Servicing because both held policies with the same insurer; Paul set a BrightRock New Business FNA plus Reduced Quote 1 and 2 for each spouse, and said Servicing must never be the default.
- **When an FNA/Shortfall/Reduced quote is being requested alongside a separate client-side document request (e.g. an updated medical/psychiatric report), do not make one conditional on the other unless the transcript or Paul says they genuinely are.** Request the quote from the insurer and request the document from the client as two independent actions in parallel — never word one as "pending"/"once received" the other unless that dependency was actually stated. **Named precedent:** [client A], 07.10.26 (review) — a first draft wrote the BrightRock Servicing FNA as "pending the updated psychiatric report", implying Sitamah should wait for the report before requesting the FNA. Paul corrected this: Sitamah emails the client for the report AND independently requests the FNA from Lizelle Cachado at BrightRock with the FF's changes and all the same loadings — the two run in parallel, neither blocks the other.
- **Debt details are captured in full, every debt (Paul's rule, 07/10/2026).** Lender/bank by name, type, term remaining, monthly repayment, outstanding balance, asset value, owner/payer, credit-life status. Only mark `Requested` if genuinely missing after checking the Audio to Text file, the transcript, the Overview, other documents, and Outlook.
- **Totals must reconcile to the cent — and debt is never excluded from a calculation by judgment call.** Whether a debt carries its own credit life cover is recorded as fact only — never a reason to exclude it from the Risk Calculation's debt deduction; that is Paul's call to make, not Claude's. Where the Audio to Text file carries its own totals (gross, net, take-home, budget, debts, childcare, risk-calculation figures), recompute them from their components and reconcile; flag any difference. **Named precedent:** [client D], 1 September 2026.
- **Flag, don't silently resolve, genuine ambiguity — but a flag is a claim too, and needs the same bar of evidence as any other field.** Don't manufacture ambiguity that isn't there — a specific, plausible value should only be flagged when a source itself contains a genuine contradiction or nonsense reading. See Step 3a for the precedent behind this caution.
- **Every "see flag" or "see notes" cross-reference must point to a flag or note that actually exists in the section it names.** **Named precedent:** [client E], 14 September 2026.
- **Derive fields the layout implies but nobody stated outright.** E.g. Date of Birth and gender from a South African ID number (first 6 digits YYMMDD; the next four digits below 5000 mean female) - and cross-check against the Audio to Text file. If a 'number of years' field holds a year (for example 2015) instead of a count, work out the years (the meeting year minus that year) and show it as "since 2015".
- **Route anything important that doesn't fit a field into that section's Notes.**
- **Pending items stay pending**, stated explicitly (e.g. "Pending — RGAR to be prepared for next meeting").
- **Dread Disease Cover Target defaults to R500,000 lump sum unless otherwise indicated.** Per Paul's standing instruction (15 September 2026). Companion rule to `fact-find-summary`'s Section 8. If the Audio to Text file shows a different dread disease figure, treat it as a deliberate entry and note the deviation and its source.
- **Standing ABI values in the Risk Calculation (Paul, 15/10/2026) — fill in automatically, every client, without asking:**

  - A different ABI sitting in the Audio to Text file for one of these is used only if Paul stated it for that client; otherwise the value above is written and the difference mentioned in one line in the section notes (this is one of the two named exceptions to rule 11). Only a different ABI that Paul states explicitly for that client overrides it, and then the deviation and its source are noted.

## Step 4: Formatting conventions (apply exactly — these came from direct advisor feedback)

- **Font:** Aptos, 12pt, throughout the entire document.
- **Every field value is point-form — this is a hard, universal rule across every output this skill chain produces, with no exceptions.** One fact per line/bullet — never run several facts together. Applies everywhere: field table cells, Notes, flags. **Named precedent:** [client A], 07.10.26 — the first draft packed multiple facts into single paragraph cells; Paul called it out as "cluttered".
- **Prior-year information is shown only if it's genuinely still true today — never carried forward by default.** Where genuinely unclear, split into two explicit lines: `[year]: [old value]` then `[year]: [current value/status]`. **Named precedent:** [client A], 07.10.26.
- **No page-number or "Page N" labels anywhere in the document.**
- **No forced page breaks between sections.** Only `keepNext` on headings and `cantSplit: true` on every table row.
- **Two-column field tables:** left column = field label (bold, light-blue shading `EAF1F8`), right column = value, bulleted per the point-form rule. Section headings in navy (`1F3A5F`), sub-headings smaller navy bold. Repeating items (debts, children, policies) are shown as one table per item, or as a table with the Audio to Text file's own columns.
