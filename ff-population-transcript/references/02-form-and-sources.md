# The form's two files, the transcript, the Overview and the Manual Fact Find

## The Fact Find (Audio to Text) file, the Overview, and the Manual Fact Find as last resort

**A. The Audio to Text file — first and primary source.**
1. **Locate it - by content as well as name.** Paul's new Fact Find form saves a data file (`.json`) and a PDF. The name stays as it always was (keep "Audio to Text"): `Fact Find (Audio to Text) - DD.MM.YYYY - [Name Surname].json` plus the same name as `.pdf`, in the client's `2. Fact Find` folder (both locations per the Client File Access order). The form's own test files may be called `Fact Find - DD.MM.YYYY - [Name Surname].json`, and a `Fact Find (Voice to Text)` name may appear, so list the whole folder, open the candidates, and recognise the data file by what is inside it (`app` is `wr-fact-find`), not by its name. Use the one dated the meeting date for this client.
2. **The program reads both the JSON and the PDF** (`run.py files`, then `run.py form`); you do not retype any value. The JSON is the first source: every field sits under `f` as a value `v` with a status `st` (`confirmed`, `preset` or `empty`; files from the older form also use `heard` and `verify`), and the repeating lists (risk policies, retirement funding, debts, children and so on) sit under `l` as rows. The PDF is the readable copy of the same Fact Find (WR Fact Find v3.0). Look at the PDF pages too. The form works some totals out only when it draws the PDF (for example the Direct Net Income, the Total Income and the Risk Calculation lines): the data file has them empty and the program lists them, so they are never lost. If the PDF and the JSON disagree on a field, the program lists it. The form's own area summaries (`sum`) and drafted action list (`pa`, `pa_actions`) are not sources: the facts come from the fields and lists, and the actions for Sitamah come from the Planner note (the Planner note, page 08).
3. **Use everything that is populated, whatever its status.** `confirmed` and `preset` values (and `heard` and `verify` values in an older file) are all populated values and all go into the Fact Find. A field counts as unanswered only when it is `empty` (or blank/"None recorded" in the PDF). Template defaults left in place by the form are `preset` values: use them, but check them against the transcript like everything else.
4. **The Audio to Text file wins; the difference is flagged.** Where the transcript/recording differs from the Audio to Text file, write the Audio to Text value and add a flag quoting both values and where each came from (for example: "Highest education: Audio to Text file says 3-year degree; on the call the client said a one-year diploma"). Never silently pick the transcript's value, and never silently drop the difference. Two things are exceptions because Paul set them as standing rules: the standing ABIs and the Dread Disease default (page 06), and the policy number, which is always taken from the actual policy schedule (page 06). Each exception is mentioned in one line when it changes an Audio to Text value.
5. **Gaps.** Where the Audio to Text file is blank, "None recorded" or `empty`, fill the gap from the transcript, then the Overview, then the client's other documents on file (page 06). A value filled from the transcript is stated as fact if clear; unclear audio is flagged, not turned into a fact.
6. **Say what you did.** The source report (page 07) states what the Audio to Text file contributed, with every `preset` entry (and every `heard` and `verify` entry in an older file) listed, as well as every difference found.
7. **Check the form's schema version every run.** Read `schema` at the top of the JSON. This skill knows `3.0`. If it says anything else (the form's code is changed from time to time), stop before building and tell Paul in one line which version you found; never guess how a new version lays out its fields.
8. **Do not process the parking list.** The JSON's `unplaced` list holds facts the form heard but did not place in a box. That is deliberate: only the crucial facts go into a field. The Teams call is recorded, so the transcript carries everything else; use the transcript for the extra context. Do not read `unplaced` as a source and do not list its entries.
9. **Use the saved value.** If a field in the file is wrong, Paul corrects it in the form himself and saves again. Never change a value because the transcript sounds different; flag the difference under point 4 as always.
10. **Check the company look-up text.** The form can look up on the web what a company does and write it into the 'what does the company do' field. Read that text before using it. Throw it out if it talks to the reader (for example "try again", "I found no...", a question) or is much longer than a short description (more than about 40 words), and replace it from what the client said in the transcript; if the transcript does not say, show `Not stated` and list it for Paul. A clean look-up that nobody confirmed is shown marked "web look-up, not confirmed with the client". If the file marks such a look-up `confirmed`, tell Paul in the hand-over message that the form's look-up should say "to verify", never "confirmed".

**B. The transcript — second, equally important source.** Read the whole transcript, start to finish, at least twice before drafting. It confirms, corrects (as a flag), and adds context to the Audio to Text file: reasons, plans, who pays what, timing. Extra context still goes in the relevant field or Notes even when the Audio to Text file already supplies the basic value.

**C. The client's latest Overview — reference.** Look in the client's `1. Overview` folder for the latest Overview (the one with the latest date in its name or modified date; the PDF and the spreadsheet both count). Use it to cross-check policies, policy numbers, premiums, cover amounts, escalation rates and group risk/retirement figures. It is a point of reference, not a primary source: it never overrides the Audio to Text file or the transcript silently. Differences are flagged. If there is no Overview, say so in the report and carry on.

**D. The Manual Fact Find — last resort, only if the Audio to Text file is absent.**
1. If, and only if, no Audio to Text file exists for this meeting (both locations checked, the whole folder listed, every candidate opened) AND Paul says to use the Manual Fact Find , look for the Manual Fact Find: Paul's filled-in copy of the WR Fact Find template, found **by content, not by file name** (`Fact Find (Manual) - [DD.MM.YY] - (Surname, First Name).pdf`, `Fact Find Template - [DD.MM.YY] - (Surname, First Name).pdf`, or similar). Open every candidate and check whether it carries entered values (form fields via pypdf, plus a rendered look). A WR Fact Find PDF with the client's name, ID, income, debts etc. filled in IS the Manual Fact Find, whatever it is called. A PDF with only template defaults ("N/A", "0.00", blank) is just the empty template. A name that does not match the expected pattern is never a reason to say it is missing.
2. Read it properly: extract form-field values AND render the pages and look at them. Tell the template defaults from real answers: a field counts as answered only when it carries a value Paul entered or a deliberate tick, or when the transcript corroborates it.
3. In that case the Manual Fact Find takes the place of the Audio to Text file as the primary source, with the same rule: where the transcript differs, the Manual Fact Find value is used and the difference flagged.
4. If neither the Audio to Text file nor a Manual Fact Find exists, continue from the transcript alone (and the Overview), say so plainly in the report, and invite Paul to point to the file if it is somewhere else. Never claim a source was consulted when it was not found, and never claim it was not found when a candidate was left unopened. **Named precedent:** [client C], 12.10.26 - the Manual FF was saved as `Fact Find Template - 12.10.26 - (Surname, First Name).pdf`; it was staged but never opened and the draft said none existed.
