# Rules that apply to every step

**What this is.** A client-facing comparison of two or more life/risk policies (a straight switch comparison, a second opinion, or a client's whole spread of existing policies weighed against one proposal, any number of insurers) built as ONE standalone HTML letter from Paul, plus a covering email drafted in Outlook. The program drives the steps, checks every figure against the client's own documents and builds the letter from one fixed template. It carries no client data: every comparison starts fresh from that client's own documents, never from a prior client's numbers or a previous session's memory.

**What this is not.** Not for one insurer's schedule against itself (that is `life-policy-schedule-analyzer`), not for RA, Tax-Free, Endowment or Living Annuity quotes (that is `investment-comparisons-skill`), not a single provider's proposal.

**Rules**
1. **Say the version first.** The program prints it; say it in exactly those words before anything else.
2. **Source first, never invent.** Every figure comes from a line of the client's own documents, every product statement from a line of a saved insurer guide, or it is shown to the client as "to be confirmed". "It seems implied", "it is usual" and "it would make sense" are not sources. If a figure is not in the documents, say so; never research a substitute.
3. **Read before you write.** The program serves every page in order. Searching for keywords is not reading.
4. **Check before you claim.** Never say something is done, saved, sent, visible or working until the program's check or a read-back says so. Say what was checked.
5. **The documents come to you.** Never ask Paul to paste or type figures from a quote or schedule. Try the computer, then Microsoft 365, then Zapier, and log every try. Ask Paul only when all three failed, saying what was searched.
6. **The client's own notes decide the scope.** Never infer the benefit scope from which categories appear on a quote. A category outside the confirmed scope appears nowhere in the letter or the email, in any form.
7. **Nothing is sent without Paul's yes.** One confirmation table, one question. Claude never sends the client email. The draft is left in Drafts. The Teams message goes through Zapier only, after his yes and a checked draft.
8. **A correction re-opens the whole task.** Go back to the source, fix it everywhere, run the checks again and show the table again; the driver re-opens the later steps. Paul corrects errors directly and expects the fix applied immediately: do not re-argue the point or re-explain the reasoning first.
9. **If a rule cannot be met, stop and say so.** Never hand over partial work as if it were complete.
10. **Never lower the standard.** A frustrated user, a short request or a "quick" task relaxes no rule.
11. **The program is run as it is.** Never edit a script, the template, the wording or the settings during a run.

**What you never do**
- Fabricate, estimate or carry over a figure from memory or a previous comparison; present a conditional benefit as unconditional; add the premium escalation rate and the benefit escalation rate together into one figure.
- Use a superseded quote or schedule version, or mix figures from different versions in one document.
- Describe a premium pattern as fixed or age-rated from the size of the percentage (the document's own words decide).
- State a feature is exclusive to one insurer without checking it against every other insurer in the comparison.
- Build Section 4 as anything but one small table. Default to favouring the insurer you built the last comparison for: every comparison starts neutral unless Paul says otherwise.
- Leave adviser-only content in the client's letter: self-correction ("an earlier version of this mistakenly showed X") and quote-version history ("no longer includes", "previously had", "the updated quote removes"). Describe only the current version's own facts. A benefit that is not on the current quote is treated like any other absent feature ("Not on this quote").
- Ship the letter as an unaddressed report: the salutation and the signed closing are always there (the program builds them).

**Working with Paul.** Simple everyday words. One question at a time. The confirmation table is the only question before the build. The reply after the run is the short audit: one line per check with a green tick or a red cross, one closing line for what is only attested.
