## UNIVERSAL OPERATING RULES - READ FIRST, APPLY TO EVERY STEP OF THE TASK

*These rules come before everything else in this skill. They apply from the first message to the last, not just at the start, and they are repeated here at the top because long conversations get compressed and only the beginning of a skill survives. If anything below seems to conflict with these rules, these rules win.*

1. **Re-load this skill before you start, and again after any compression.** At the start of every run - and whenever the conversation has been summarised or compressed, or has run long - open this skill in full (Skill tool) and re-read it before you produce or change any deliverable. Never work from a summary of the rules or from memory of them.
2. **Source first - never invent.** Write only what is in the source material (transcript, quote, document, file) or in a named document this skill tells you to use. If a line is unclear, garbled or ambiguous, do not turn it into a fact: flag it to the user. "It seems implied", "it is usual" and "it would make sense" are not sources.
3. **Read before you write.** Read the source material completely and carefully - at least as many times as this skill requires - before drafting anything. Searching for keywords is not reading.
4. **Check before you claim.** Never tell the user something is done, saved, sent, visible or working until you have checked it yourself (open the file, list the folder, look at the screen). Say what you checked.
5. **Deliver everything this skill lists, every time.** A run is not finished until every deliverable this skill names has been produced AND handed over exactly the way this skill specifies (shown in chat, sent as a file in the chat, saved to the named folder). Before you reply, list each deliverable and confirm each was handed over.
6. **Every correction re-opens the whole task, not just the item.** When the user corrects anything: (a) go back to the source and re-check that point and everything related to it; (b) fix it everywhere it appears, in every deliverable; (c) re-run this skill's full checklist; (d) re-deliver every affected deliverable in full, as in rule 5. Never fix only the item named and stop.
7. **Never lower the standard.** A correction, a frustrated user, a short request or a "quick" task does not relax any rule in this skill.
8. **If a rule cannot be met, stop and say so.** State exactly which rule or step could not be completed and why. Never hand over partial work as if it were complete.
9. **Changes to a skill:** edit the existing skill, never create a new one. Update its "Last updated" stamp (Athens time) and changelog. Then put the full updated SKILL.md forward for the user to review and save using the propose_skills tool (the "Update skill" review card). Never say the change is live until the user confirms they saved it. If the card does not appear, say so plainly and ask the user how to proceed - do not claim it was delivered.

**Delivery gate for this skill (rules 5 and 6 applied):** a run is complete only when ALL of these are done and confirmed in one line each: (1) every board change was made, the "Last updated" stamp was bumped, a Change Log entry was added, and the board was republished in the same reply with the publish result checked (see Publishing); (2) whenever a Fact Find is processed, all three outputs - the Fact Find Transcript PDF, the Fact Find Summary PDF and the Planner / AdviceTech note - were delivered together in the same turn; (3) every referral or provider email this skill drafts was shown to Paul for approval before anything was sent. After ANY correction, repeat (1) to (3) for everything that changed.

Note that editing the draft body afterwards can drop the quoted thread below the reply — re-check the draft. Paul sometimes sends the draft himself: check Sent Items before telling Sitamah to send it, and don't ask her to send something already sent (ask her to chase instead).

## Board sections

**Prospect** (client-level) — a short log of contact/booking activity. For a brand-new prospect this is a genuine intake log; for an existing client this section still appears but is labeled **"Existing Client"** rather than omitted. No Identified/Actions Taken shape here — just a simple entry log.

**Fact Find** (client-level) — **Identified only.** One plain point-form list of what the FF actually says, product by product. No "needed" split, no per-fact log entries, no Actions Taken on this card. **Also captures the confirmed follow-up/2nd appointment date**, if set — see "Follow-up appointment tracking" below.

**General** (client-level, sits right after Fact Find) — the one section that talks to the client about documents:
- **Before writing Identified, check what's already on file.** Look in the client's OneDrive folder, subfolders **"3. LOA & Disclosure"**, **"4. FICA & POI"**, and **"6. Policy Schedules"** (device bridge, see `/topics/tools.md`) — 6. Policy Schedules is mandatory, not optional (an existing RA statement has been missed there before). Open each candidate PDF rather than trusting the filename — an MSIGN-signed document carries audit-trail pages (signer, completion date) that confirm it; a filename saying "signed" alone is not proof, and a same-named file with no audit trail is likely still the blank template. **Corrected 2026-09-16 — a password-protected statement is logged as found-but-locked, and Claude does not ask the client for the password.** Instead, message Sitamah (Action needed — see `sitamah-messaging.md`) that Claude needs access to check that policy schedule, and ask her to re-save it in the client's OneDrive folder without password protection. Anything confirmed on file goes in Identified, not the client ask (e.g. "LOA + Disclosure — both on file, signed [dates]. No client action needed."). Anything on file but stale (POI/proof of address older than ~3 months) is logged as on file *and* flagged for a refresh. A genuinely absent item goes on the ask normally.
- **Identified:** every document the FF shows WR doesn't yet have, from every product, gathered into one list, reconciled against the OneDrive check above.
- **Pending:** the single question — "Ready to send [Client] one email for [documents]?" — until Paul answers.
- **Actions Taken:** the moment Paul says yes, in the same reply, draft the consolidated email and save it to Outlook Drafts: **To** the client's FF-captured email, **CC Sitamah**. Body lists the documents plainly. **Corrected 2026-09-16 — the LOA/Disclosure signature request is no longer part of this email**; it's its own dedicated auto-built, chat-approved, Claude-sent line (see `core-ff-intake.md` → LOA/Astute sequencing gate) — General's consolidated email covers the other client documents only (policy schedules, POI, GR statement, etc.). No typed sign-off. **Corrected 2026-09-16 — the moment the draft is saved, message Sitamah (Action needed, see `sitamah-messaging.md`): she checks it and sends it herself if correct, and follows up with the client periodically before the next appointment.** This replaces Paul as the one who sends General's consolidated email — he's still CC'd and can see it, but Sitamah owns the actual send here. Clear the pending question and log what was drafted as separate short bullets (e.g. "Document-request email drafted, saved to Outlook Drafts. To [Client], CC Sitamah.", "Requests: [documents].", "Sitamah asked to check, send, and follow up.").

**Product lines** (Life Cover, Retirement Annuity, Investments, RGAR, EGAR, Medical Aid, Will, Short-Term Insurance) — created from the Fact Find, one card per product need, each the same shape:
- **New Business/Servicing tag (Life Cover, RA, Investments only):** the one internal flag that *does* show on the board — set by asking Paul directly the moment the line is created. RGAR/EGAR/Medical Aid/Will/STI never carry it.
- **Identified:** numbered, short — what the FF says this product needs, including any provisional/unclear item flagged plainly (e.g. "Group Risk unclear — client not sure, see General for the statement request").
- **Pending:** the single next question to the provider/insurer. For Life Cover specifically, this is **one combined question covering everything answerable right now** (which insurer for FNA, plus — if GR is still unclear — whether to proceed with a Reduced Quote now on an FNA basis and with which insurer), not three separate one-at-a-time asks — the Shortfall question is genuinely later, not just batched differently, since it can only be asked once the GR Benefit Statement actually comes back (see `playbooks/life-cover.md`). **RGAR and every Claude-drafted proposal are auto-draft lines** — no pending question; Claude drafts straight to Actions Taken. **Short-Term Insurance, Medical Aid, and Will are auto-*built* but not silent** — each one's pending question is the built email itself, waiting on Paul's chat approval to send (see `playbooks/short-term-insurance.md` and `playbooks/medical-aid-will.md`, and `cameron-short-term-skill` for STI) — different from a true auto-draft line and from Life Cover's combined-question pattern.
- **Actions Taken:** numbered, short — quote request, drafted proposal, pre-filled application, submitted application, referral, policy issued, ROA/SROA. The running record of the product's journey; appended as work happens, never restating an Identified fact as an action.

A new product line is created either from a Fact Find or later when Paul reports a new need. Every new line gets the New Business/Servicing question immediately.

## Board change log

- **Why:** the board only ever shows current state — no record of what it said last week, and no single time-ordered view across cards of what happened when (a card's own Actions Taken is organized by product, not by date, and nothing on the board is currently dated per-event). This section is the fix, and it's genuinely new information, not a duplicate of Actions Taken — it's the same facts organized by *when*, with a real date attached, instead of by *which card*.
- **Location:** its own section at the very bottom of the page, below every product card, titled "Change Log."
- **One entry per republish, always** — since a republish only ever happens because something changed (see Publishing), every republish gets an entry; there's no "quiet" republish to filter out.
- **Format:** the date (Athens time, same convention as "Last updated"), then one or more short point-form bullets — same brevity discipline as Actions Taken, one fact per bullet — naming which card(s) changed and what happened. Cross-reference, don't duplicate: "Life Cover: FNA quote drafted, sent to Lizelle" is enough; the full detail stays on that card's own Actions Taken.
- **Newest entry at the top.**
- **No cap under normal use** — a client's full journey realistically runs to a few dozen entries, trivial as plain text. If a long-running Active client's log genuinely passes ~40 entries (several review cycles), collapse everything older than the most recent ~15 under a native `<details>`/`<summary>` fold ("Show earlier changes") rather than deleting anything.
- **Populated automatically, same as the rest of the board** — no separate go-ahead; it's part of the same republish that updates the card(s) it's logging.

## Board close-out

- **What this is for.** Boards and chats currently accumulate forever — there's no step that ever says "this one's done." Most clients never need this: an **Active** client's board stays open indefinitely, since new servicing needs and annual reviews keep creating new activity on the same board — that's the model working as intended, not something to close out. Close-out is only for the two genuinely terminal cases, using Paul's own existing classification language (see the Master Context Document's Client Classification): **NTU** (declined everything at prospect stage, no policy ever placed) and **Inactive** (was an active client, relationship has ended — no active policies, may re-engage later).
- **Never auto-close — always ask, once.** The moment every open product line on a board has resolved to either NTU/declined or Complete-with-nothing-further-expected, and the client-level question hasn't been asked yet, ask Paul directly: **"Every line here is resolved — is [Client] fully closed out (NTU or Inactive), or should the board stay open?"** If he says stay open (e.g. he expects to re-approach an NTU prospect later, or an Inactive client may return), don't ask again until something changes materially — don't re-ask on every subsequent republish.
- **What close-out actually does, once Paul confirms:**
  1. Add an unmistakable banner at the very top of the board: **"CLOSED — [NTU / Inactive] — [date]"** (Athens time).
  2. Cancel any scheduled triggers still running for this client — the daily outstanding-request check (`outstanding-tracking.md`), any follow-up check-in — via `delete_trigger`. A closed client shouldn't still be polling Outlook every day.
  3. Add a final Change Log entry recording the close-out and the reason, same as any other entry.
  4. Republish with the banner — this is the one time a republish happens specifically *because* of a status change rather than a card update.
  5. **Update the board index** (`board-index.md` at the project level) — change this client's Status column to reflect the close-out, so the one place Paul actually gets a cross-client view stays accurate. This is the same file already updated whenever a board is created or its status changes materially.
- **Never delete the chat or the board.** Close-out means clearly marked and inactive, not gone — the history stays available if the client re-engages or the NTU decision gets revisited.

### Reading a WR Fact Find's actual values
The WR Fact Find is a fillable AcroForm PDF — plain text extraction returns only static labels, never the client's actual answers, which live in form field objects with opaque names (`dropdown_45oakx`). To get real answers: (1) read form fields directly, e.g. `pypdf`'s `PdfReader.get_fields()` for each field's `/V`; (2) match each field to its on-page label by position — field rects via page annotations, label words via `pdfplumber`'s `extract_words()`, nearest label to the left/above; (3) cross-reference the resulting values against the per-service decision logic below and the Master Context Document; (4) do this once per Fact Find, automatically, not only when Paul asks a follow-up question.

**A decision-driving field contradicted by its own note is provisional.** If a Yes/No feeding a decision (Group Risk Cover, a "does client require X" toggle, a named specialist-contact field) is contradicted by its adjacent note — box says Yes, note says "client not sure" — apply the literal answer so nothing's missed, but flag it plainly in the relevant Identified line (e.g. "Group Risk unclear — FF says Yes, noted 'client not sure'").

# Keeping Sitamah in the Loop

> Loaded from `sitamah-messaging.md`, referenced by the core `SKILL.md`. Full trigger list, message-writing rules, and worked examples for every Teams message Sitamah receives.

## Keeping Sitamah in the loop

Sitamah gets a Teams direct message for every instance below, in addition to — never instead of — her email CC and the board's own log. More information is better here; this list is deliberately not trimmed to "important" ones only.

**Two tiers, so the messages that need her to actually do something don't get lost in the ones that don't.** Every trigger below is one or the other — never both, never neither:

- **Action needed** — the message asks Sitamah to do something (now or "watch for X and follow up if it doesn't happen"). Tag it: the first line after the greeting is **`Action needed:`** followed by a one-clause summary of what, before any other detail. This is deliberate — Teams often shows a message's opening words in the notification preview, so the tag surfaces there too, not just once she opens the chat.
- **FYI** — nothing for her to do; the message is purely so she stays current. No tag needed (its absence *is* the signal) — but it must still end with an explicit "nothing needed from you" line, same as before. Never leave an FYI message ambiguous about which tier it is.
