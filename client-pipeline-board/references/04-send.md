The order after Paul's yes: emails first, then the Sitamah messages, then the check-in. Each is read back and checked by the program.

**Emails.** Create or send exactly what `out/email_<id>.json` says, with the native Microsoft 365 tool (never Zapier). Record `email.<id>.created_with` (the tool name) and `email.<id>.draft` or `email.<id>.sent` (the id it returned). Read the saved item back (the draft from Drafts, or the sent email from Sent Items), save it to a file and run `run.py email`. A wrong draft is never sent: fix it in Outlook and read it back again. Never send a request that should have been a reply.

**Teams messages to Sitamah** (Sitamah Nathoo, the 1:1 chat, through Zapier only, format markdown, after Paul's yes and the checked emails). Two tiers, so the messages that need her to act do not get lost:
- *Action needed*: the first line after the greeting is `Action needed:` and a one-clause summary (Teams often shows the opening words in the notification). The program has the wording for each: an email sent that needs a reply watched for; the daily outstanding check still has items with no reply (it names the contact for each, and states the real check cadence read off the scheduled task, never "regularly"); the Lizelle attachment (four steps: open, attach, send, follow up with Lizelle); the LOA email sent (prepare the MSIGN pack from the pre-populated LOA and Disclosure); a locked policy schedule; General's consolidated email drafted (check it, send it if correct, follow up with the client periodically before the next appointment); the signed LOA saved (draw the Astute report); the COC invite sent (watch for acceptance); the day of the COC appointment (call the client as a reminder); one hour after the COC (confirm whether it happened; the tele-underwriting transcript is requested only once she confirms); an RAR request drafted; a follow-up check-in that came back moved or not accepted.
- *FYI*: no tag, and it ends "Nothing needed from you." It covers every ordinary Actions Taken entry (a request drafted or received, a proposal saved, an application pre-filled, a submission sent, FICA, a Welcome Letter or policy received, an ROA or SROA completed, a referral sent) and Paul-reported milestones (the client's decision at presentation, an application dated live, COC accepted, a counter-offer and how Paul answered, the policy in force, the follow-up meeting having happened). One FYI message per run, in point form. When a product skill already messages her for the event (proposals, the Short-Term referral, the invite), the board sends nothing for it.
- A message covering both resolved and still-outstanding items is Action needed overall; the resolved half stays a plain FYI note within it.
- Always make clear it is Claude, not Paul. Plain, warm language: no stage codes, no internal jargon. Point form for more than one fact. The greeting comes from the South African clock when the message is sent (before 12:00 "Good morning", 12:00 to 18:00 "Good afternoon", after "Good evening"; "Hi" for any later message the same day); the program sets it.
- Resolve her chat once with `list_dynamic_enum_values` on `microsoft_teams_send_chat_message`'s `chat` property and reuse it. If the native Teams send fails for a missing scope, Zapier is the route. Read the posted message back and run `messagecheck`.

**Same-day check-in** (only when a follow-up date was entered). A scheduled task bound to this chat (`create_trigger` / `send_later`, never the local in-session cron tools, which do not survive), timed for the morning of the appointment: is the meeting still on and accepted? The program prints the exact settings. A move: cancel the old check-in first (`delete_trigger`, receipt `checkin.deleted`) and update the existing invite in place. If the check-in finds the meeting moved or not accepted, tell Paul plainly and message Sitamah (`followup_moved`). If a meeting was booked outside Outlook the check-in will find nothing to confirm: say so rather than assuming it did not happen.

**Outstanding requests.** Reply tracking is owned by `outlook-emails-skill` (an hourly weekday watcher per thread and a one-time silence flag, a fresh chat each time, a phone alert). Log every outbound request against its product line the moment it goes out. A check for a file dropped into the client's folder (a quote PDF, a signed LOA) is a separate text rule: search the client's folder for a matching new file, save it by the routes in `01-locate.md`, clear the outstanding item and log it under Actions Taken. Finding something is a fact, not a decision: log it without asking; if it needs a decision from Paul (a counter-offer, an insurer's question) it becomes the pending question. When something is found, tell Paul with a push notification. This folder check is unproven. Pulling an attachment out of a reply email is also unconfirmed: no dedicated tool exists; tell Paul plainly whether it worked, and fall back to asking him or Sitamah to save it.
