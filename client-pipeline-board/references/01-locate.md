Locate = the client, the existing board, the documents on file. The program logs every try.

**The client.** Read the client's name off the chat title (Paul always names the client or prospect there). Ask only if the title genuinely does not make it clear. The ONLY question asked before work starts: is this a brand-new prospect, or an existing client? Both get the Prospect section; an existing client's is labelled "Existing Client". Record his answer in the first change (`init`).

**The board.** If a board for this client exists, read the published page back (the Artifact tool) and load it with `run.py base`: the program checks its checksum and that it is this client's. If it was edited by hand or damaged, stop and tell Paul. A new client: say there is no board yet, in Paul's words (`--first-board yes`). Log how you looked.

**The three routes, in order.** 1 the computer (local drive / OneDrive), 2 the Microsoft 365 connector (SharePoint), 3 Zapier. Try them in this order and log EVERY try, failures too. Never say "I cannot access your files" without a log of all three. Paul is asked last, with proof of what was searched. While a scheduled check runs unattended there is no computer: use the Microsoft 365 route. `sharepoint_upload_file` caps at 1 MB per file: flag a larger scan to Paul instead of failing silently.

**The transcript.** Search the client's folder for the 1st appointment transcript yourself, without asking first. Found: run `ff-population-transcript` on it directly (also for a later or servicing Fact Find). Only if it is genuinely not there, ask Paul to upload it. If no transcript exists anywhere and Paul points to an already-completed Fact Find: run `fact-find-summary` on it directly. That shortcut is only for a genuinely new prospect: a Servicing line always runs a fresh, full Fact Find from a current transcript.

**The three outputs (every Fact Find processed).** The Fact Find Transcript PDF, the Fact Find Summary PDF and the Planner / AdviceTech note, delivered together in the same turn. No field taken from a transcript may be marked "Not discussed" without an actual re-check of the transcript (see `fact-find-summary`'s transcript-accuracy rule).

**What is already on file (before General's list is written).** Look in the client's folder, subfolders `3. LOA & Disclosure`, `4. FICA & POI` and `6. Policy Schedules` (the last is mandatory: an existing RA statement has been missed there before). Log each folder with `run.py access --purpose onfile` and the folder name in the note: the program refuses General's list until all three are logged. Open each candidate PDF rather than trusting the filename: an MSIGN-signed document carries audit-trail pages (signer, completion date); a file called "signed" with no audit trail is probably still the blank template. A password-protected statement is logged as found-but-locked: do not ask the client for the password; tell Sitamah (message `locked_file`) to re-save it without protection. Do not put anything on the client ask that is already signed or on file; flag anything on file but stale.

**A Fact Find checkbox is not a document in hand.** Where a decision depends on a document WR does not yet have (Group Risk Benefit Statement, existing policy schedule, RA or pension statement, proof of income, investment statement), request it through General and keep the dependent quote out of Actions Taken until the document is actually back, even if the Fact Find says the cover exists. A BrightRock Shortfall quote needs the real Group Risk Benefit Statement, not just "Group Risk Cover: Yes": say so in the pending question.

**A field contradicted by its own note is provisional.** If a Yes/No that drives a decision (Group Risk Cover, a "does the client require X" toggle, a named specialist) is contradicted by its adjacent note, apply the literal answer so nothing is missed, but mark the Identified point provisional with the reason ("Group Risk unclear: the form says Yes, the note says client not sure"). A genuine contradiction should be rare. If one turns up (required but unaffordable, or a Yes/No disagreeing with its own note), do not silently decide: flag it on the Fact Find card and ask Paul what to do. Never skip the product line unasked.

**LOA and Astute (sequencing gate).** The LOA explanatory email always goes out before the MSIGN signing pack, and the Astute report is never drawn until the signed LOA is back. The LOA email is its own line (route `loa_email`: built by the chat, shown complete, sent after Paul's yes), not part of General's consolidated email. Before asking Paul: locate the client's LOA and Disclosure templates in their folder and pre-populate both from the Fact Find; tailor the LOA email from the standing template in Outlook Drafts. When the signed LOA is saved, tell Sitamah (message `astute_loa_signed`) to draw the Astute report: Claude does not draw it. `astute-summary-report-skill` summarises it afterwards.

**Testing.** The program is tested on an invented client. The first real run is Paul's.
