You never write the Markdown. You write ONE file, `record.json`; the program checks it against the raw notes and draws the record.

```
{"fields": { "<field name>": ... },
 "notes": {"blocks": [{"from": [3], "date": "2022-02-14", "bullets": ["...", "..."]}]},
 "left_out": {"<token as the program shows it>": "reason"},
 "merge_notes": ["what the earlier version added"]}
```

**The 18 fields, always in this order** (the program draws them in this order; leave one out and it reads `Not recorded.`): Full Name, Last Name, First Name, Known As, Categories, First meeting, First policy signed, Portfolio Review Month, Got details from, Client ID No, Income Tax Number, Adviser Allocation, Medical Aid, Short Term Insurance, Family Information, Life & Investments, Notes, Commission.

- **Fields 1 to 12** are text exactly as the source gives it; the program proves each is character for character in the raw notes. Never invent, infer or fill in. **Known As** only if the source explicitly gives a nickname or preferred name. **Categories** exactly as stated (`Client`, `Client / BrightRock Lead`, `Client / Non-Replacement`).
- **Medical Aid / Short Term Insurance**: text, or a list of lines. If the source says "not brokers yet" with a blank contract: `Contract: Not recorded / not brokers yet.` If there is substantive detail (insurer, premium, coverage notes), reproduce it in full.
- **Family Information**: a list, one member per bullet: name, relationship, and any extra detail given (ID numbers, "also a client", contact numbers). A dependant's linked policy details go under that member's entry.
- **Life & Investments**: `{"previous": [...], "current": [...], "inactive": [...]}` (Previous/Replaced, Current/Active, Non-active/Lapsed), each policy `{"contract", "product", "doc", "premium" (optional), "status" (optional, caps as given), "flag" (optional)}`. The program draws `- Contract: [number] ([Product / Insurer]) DOC [date] / [premium if stated] / [STATUS]`. Contract numbers, DOC dates, premiums and status notes are reproduced verbatim: do not reformat or clean up. Apparent typos or inconsistencies are preserved and flagged with a `flag`. An empty group reads `- Not recorded.`
- **Commission**: `[{"title": "Insurer – Product Description (Month 'YY)", "lines": ["1st year comm: R...", ...]}]`, every line verbatim. No commission recorded: `- Not recorded.`

**Notes.** `blocks` in date order, oldest first. Each block: `from` (the entry numbers of the raw notes it summarises) and `bullets`; `date` only when it differs from the entry's own date. The program draws the BOLD ALL CAPS heading: a day heading (`14 FEBRUARY 2022`) when the entry has a day, a month heading (`MARCH 2024`) when it has only a month; no underline tags and no HTML. **Summarise, don't transcribe:** condense each entry into short, tight bullets, keeping every fact: who, what, which policy or contract number, amounts, dates, decisions made, next steps. Sub-lists (an FNA breakdown, medical requirements, shareholding details) stay as indented bullets, tightened where nothing is lost. Do not omit an event, figure or outstanding item to save space: length follows the number of distinct facts.
- **Multi-part requests and advisor decision-points (CRITICAL).** When a client asks "which X should I do Y from", capture what is asked (for example a R70k withdrawal), which products or accounts are in play (by contract number and product type), which option(s) the advisor recommended or is considering, the rationale (tax, fund values, withdrawal rules) and what the client decided or what is pending. Example: "Client asked which OM products (RA (contract no.), Tax-Free (contract no.), Funeral (contract no.)) to withdraw R70k from. Paul advised on options; client deciding which to use." NOT "Client asked about OM withdrawal". The program checks every contract number and amount of that raw entry is in the bullets.
- **Quoted text** from emails or messages only when the exact wording matters (an explicit instruction, a commitment, a "do not contact" request, anything that could matter in a dispute); otherwise summarise. Keep a quote short and include its timestamp.
- **MS Planner links** are rendered `[Planner – Task Name](URL)` with the anchor text matching the Planner task name exactly; links are never summarised.
- **"Do not contact" and "do not call" instructions** are found by the program in the raw notes. Reproduce the line in full in its dated bullets, never summarised; the program adds the warning at the top of Notes itself and refuses the record if the line is missing.
- **Flags.** The program adds, at the top of Notes, the warnings it finds in the raw notes: a number that differs by one character from another (an apparent typo), a number in scientific notation or a truncated ID (not presented as exact), an ID that fails its check digit or looks like a policy number, timestamps that look system-generated. Add your own `⚠️` bullets for what only you can see: notes that look lost, an outstanding item never actioned, a header number that looks like a policy number rather than a client ID.
- **left_out.** The program lists every date, amount, percentage, number, contract-like code, email, link, name and abbreviation of each raw entry that is not in the record. Keep it, or list it in `left_out` with a reason; Paul sees that list. Do not expand an abbreviation (see `06-reference.md`).
