Contents: how to derive each answer (Step 0b), the answers file, and the rules the program applies.

**Derive first, ask last.** Do not ask the setup questions one by one when the client's file answers them. Read, in this order: the latest "WR Overview" PDF; the insurer application (client name and ID, personal or business cover lines, the replacement section, accepted benefits); the latest Follow-Up Appointment Summary Notes (what was accepted and when, replacement context, risk tolerance, insurers compared); the client's email confirmation (Outlook, matched on the subject thread); the Risk Tolerance questionnaire (`WR - New Risk Tolerance - ...`, the "Calculated category"; if none was completed, ASK Paul before building); the quotes in `Comparative Quotes`. Then the program shows Paul ONE confirmation table (question | answer | source). Ask him only about genuine gaps or conflicts. Use a button-style question for any fixed set of options (bundle, personal or business, replacement, taken up or declined, risk profile, the Investment need) and typed input only for things with no fixed list.

**Source rules per answer**
- **Bundle and Personal/Business:** the Follow-Up Notes, the application's cover-lines selection and the transaction folder name.
- **Insurers considered:** default = the recommended insurer ONLY (1 to 3, never padded). Add another only if the Overview lists it, the `Comparative Quotes` folder genuinely holds a quote from it, or the Follow-Up Notes say it was compared. Existing policies being replaced are not "considered". Retirement and Investment: also ask which is the Recommended Insurer, as its own question.
- **Recommended vs Taken Up (Risk):** Recommended = the FNA quote; Taken Up = the LATEST accepted quote (Reduced or Revised), per cover type, both read from the top-level "Summary" block ("Value of your cover"). That's caused by death = Life Cover; That's permanent = Lump Sum Disability; That you can recover from = Income Protection (monthly); Additional expense needs = Dread Disease. **The premium for the reference number and the file name is the "Total premium" printed INSIDE the accepted quote**, not the quote's file name, the Overview or the application.
- **Replacement, Risk:** per cover type, from the application's replacement section matched to cover types using the Overview and the policy schedules. If a replaced policy cannot be matched to a cover type, ask.
- **Replacement, Retirement and Investment:** asked once. When the client has other Risk Cover in force that this transaction does NOT replace, set `other_risk_cover_in_force` true: the reason text then ends with the verbatim sentence "Although the client has other Risk Cover in force, this transaction does not constitute a replacement of that cover."
- **Retirement and Investment extras (asked, never inferred):** `product_provider` and `product_name` (for example Old Mutual, Retirement Annuity Xtra Max); `frequency` lump_sum or monthly; the amount is the confirmed accepted amount from the client's own reply, never the amount first proposed if the go-ahead was for a different figure; Investment only: `need_identified` is Children Education Planning or General Investment Planning.
- **Old Mutual Tax-Free Investment shortcut:** product provider Old Mutual, product name Tax-Free Investment Plan, recommended product `Old Mutual - Max Investment`; still ask lump sum or recurring.
- **ROA date:** the date of the client's written reply (it always takes priority); if the go-ahead was verbal, the date of the adviser's recap email. A transaction can go through several proposed amounts: use the date the client agreed to the figure the ROA is built for. **Risk exception (Paul):** verbal acceptance in the Teams meeting is enough: take the date from the latest Follow-Up Notes, but if a written client reply or recap email has a different date use the written one and tell Paul. Retirement and Investment still need the client's own reply email. `roa_date_source.type` records which.
- **Client name and ID:** from the application, cross-checked with the Fact Find Summary and the quote. ID: 13 digits, no spaces, no dashes. The ROA keeps the ID in the confirmation line.
- **Risk profile:** the Risk Tolerance questionnaire, confirmed by the Follow-Up Notes.
- **Conflicts:** if two sources disagree (other than the premium rule and the verbal-acceptance date rule), list it under `conflicts`: the program refuses to go on. STOP and ask Paul, quoting both values and their sources.

**The answers file (JSON).** Top level: `bundle` (risk | retirement | investment), `client_name`, `client_id`, `risk_profile`, `roa_date` (DD/MM/YYYY), `roa_date_source` {type: client_reply_email | recap_email | follow_up_notes, file}, `insurers_considered` (list), `recommended_insurer` (CAPITALS as in the template's list, for example BRIGHTROCK; an insurer outside the list is written in CAPITALS and Paul is told), `sources` (one source, a document or Paul's words, for each of: bundle, client_name_id, risk_profile, insurers, roa_date, and Risk: scope, replacement, taken_up, premium, amounts; Retirement/Investment: product, amount, replacement), `conflicts` ([]).
- **Risk:** `scope` (personal | business), `premium` ("R 1 172.80"), `covers`: exactly death, disability, income_1st24, dread. Each: `state` = accepted | not_accepted (FNA done but the benefit was not taken up: taken-up amount R 0, section stays IMPORTANT) | declined (declined outright without an FNA: needs `declined_reason` that Paul gave and `declined_source`) | not_pursued (the need exists but the client does not want it now: fixed sentence); for accepted and not_accepted: `replacement` true/false (per cover type), `recommended_amount`, `taken_up_amount` (whole rands), `recommended_product` (a dropdown product), `scenario` (the exact bank heading, for example "FNA DONE & ACCEPTED / REPLACEMENT:", which must agree with `replacement`), for disability and income_1st24 `need_identified` ("Lump Sum Disability Cover" and "Sickness and/or Income Protection Cover"; without it the field renders blank), income_1st24 is monthly. A cover type that is NEW while the client's other cover is replaced or stays in force: `new_while_other_replaced` true with a NON-REPLACEMENT scenario; the program ends the paragraph with the verbatim "other Risk Cover in force" sentence. If NO bank scenario fits, give `custom_reason` in Paul's own wording; it is marked CUSTOM in the table and the audit. Never enter income_after24 (always Do not Review with a fixed sentence) or health care.
- **Retirement / Investment:** `product_provider`, `product_name`, `amount`, `frequency`, `recommended_product`, `replacement`, `other_risk_cover_in_force`, `need_identified` (Investment only), `reply_email` {from (the client's own address), sent, to, cc, subject, acceptance_text (the client's own words, for example "kindly proceed with the attached")}.
