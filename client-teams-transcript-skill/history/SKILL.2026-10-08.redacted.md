# Client Teams Transcript Skill

## UNIVERSAL OPERATING RULES - READ FIRST, APPLY TO EVERY STEP OF THE TASK

*These rules come before everything else in this skill. They apply from the first message to the last, not just at the start, and they are repeated here at the top because long conversations get compressed and only the beginning of a skill survives. If anything below seems to conflict with these rules, these rules win.*

1. **Re-load this skill before you start, and again after any compression.** At the start of every run - and whenever the conversation has been summarised or compressed, or has run long - open this skill in full (Skill tool) and re-read it before you produce or change any deliverable. Never work from a summary of the rules or from memory of them.
2. **Source first - never invent.** Write only what is in the source material (transcript, quote, document, file) or in a named document this skill tells you to use. If a line is unclear, garbled or ambiguous, do not turn it into a fact: flag it to the user. "It seems implied", "it is usual" and "it would make sense" are not sources.
3. **Read before you write.** Read the source material completely and carefully - at least as many times as this skill requires - before drafting anything. Searching for keywords is not reading.
4. **Check before you claim.** Never tell the user something is done, saved, sent, visible or working until you have checked it yourself (open the file, list the folder, look at the screen). Say what you checked.
5. **Deliver everything this skill lists, every time.** A run is not finished until every deliverable this skill names has been produced AND handed over exactly the way this skill specifies (shown in chat, sent as a file in the chat, saved to the named folder). Before you reply, list each deliverable and confirm each was handed over.
6. **Every correction re-opens the whole task, not just the item.** When the user corrects anything: (a) go back to the source and re-check that point and everything related to it; (b) fix it everywhere it appears, in every deliverable; (c) re-run this skill's full checklist; (d) re-deliver every affected deliverable in full, as in rule 5. Never fix only the item named and stop.
7. **Never lower the standard.** A correction, a frustrated user, a short request or a "quick" task does not relax any rule in this skill.
8. **If a rule cannot be met, stop and say so.** State exactly which rule or step could not be completed and why. Never hand over partial work as if it were complete.
9. **Changes to a skill:** edit the existing skill, never create a new one. Update its "Last updated" stamp (Athens time) and changelog. Then put the full updated SKILL.md forward for the user to review and save using the propose_skills tool (the "Update skill" review card). Never say the change is live until the user confirms they saved it. If the card does not appear, say so plainly and ask the user how to proceed - do not claim it was delivered.

**Delivery gate for this skill (rules 5 and 6 applied):** a run is complete only when ALL of these are done and confirmed in one line each: (1) Output 1 (Planner note) shown in the chat as formatted text; (2) Output 2 (PDF) sent in the chat for the user to download and review; (3) the same PDF saved in the client's `2. ## Where this skill sits in the client journey

1. **First meeting (Fact Find):** `ff-population-transcript` builds the Fact Find Transcript PDF, then `fact-find-summary` builds the Fact Find Summary PDF.
2. **Every follow-up meeting (one or many):** this skill. It produces the Follow-Up Appointment Summary Notes PDF and the Planner/AdviceTech short note, checks the applications against what was said, and has them corrected.
3. Because follow-ups build on each other, **this skill must never summarise a meeting in isolation** - Step 2 (context pack) is mandatory every time.

**Output 1 now applies to every meeting, first appointment included (changed 07.10.26, reversing the 06.10.26 exception).** `ff-population-transcript`'s Step 7b calls through to this skill's Output 1 section directly for the Fact Find/first-appointment Planner note - there is no separate bespoke layout for it any more. Two things differ for a first/Fact Find meeting, nothing else: (a) the **pointer line** names the **Fact Find Summary PDF** rather than a Follow-Up Appointment Summary Notes file, since the latter doesn't exist yet at this stage; (b) the **Applications** section is typically omitted (no applications stage has normally happened yet). **Output 2 (the Follow-Up Appointment Summary Notes PDF) is still never produced for a first/Fact Find meeting** - the Fact Find Transcript and Fact Find Summary PDFs remain that meeting's documents, and this skill's Step 2 context-building, Step 2b (applications) and Step 6 (application corrections) are skipped when there is nothing yet for them to act on. Everything else in this skill (Steps 1-5, Accuracy, Output 1's design) governs the Fact Find meeting's Planner note exactly as it governs a follow-up's - **including the Two-Read Lock in Step 1b.**

**Two deliverables for a follow-up meeting:** Output 1 (Planner note, shown in chat as formatted text) and Output 2 (PDF, saved to the client's folder and sent in chat). For a first/Fact Find meeting, only Output 1 comes from this skill (Output 2 is the Fact Find Summary, produced by `fact-find-summary` instead). Never save copies of Output 1 anywhere else. The only other thing this skill causes to be written is the correction of the client's application PDFs, which is done by `complete-applications-skill` in place in the client's own `Applications` folders (Step 6) - never by this skill itself, and never at a first meeting.

## Step 0: Locate the transcript

- If Paul's message reads `[Client] - Appointment transcript summary - DD/MM/YYYY`, that date is the meeting date. Look for `Teams meeting transcript - DD.MM.YY - ...` (.docx) in the client's `2. Fact Find` folder; match loosely (typos happen). Never fall back to the newest file when a date was given. Dates are always DD/MM/YYYY.
- No date given: take the newest unsummarised transcript and mention any older unprocessed ones.
- Stage it with `device_stage_files`, read with `pandoc -t plain --wrap=none`.
- Not in the folder yet: if the meeting has finished, use the `client-transcript-download` skill to fetch it (Claude in Chrome), then continue. If that is not possible, ask: "Please upload this client's Teams Meeting Transcript". Never summarise from a title or memory.
- A WhatsApp call has no transcript file: see the WhatsApp section.
- **For a first/Fact Find meeting reached via `ff-population-transcript`'s Step 7b, the transcript is already in hand (passed in directly)** - skip the locating, but NOT the two reads: go straight to Step 1b and do both reads there.

## Step 1: Verify the transcript is complete

Compare the stated total duration with the last timestamp; check for jumps. If truncated or gapped, say exactly what is missing and stop.

## Step 1b: THE TWO-READ LOCK AND STRICT COMPLETENESS PROTOCOL (Paul's absolute rule, 08/10/2026 - non-negotiable, there is NO way around it)

**THE LOCK: this skill is NOT ALLOWED to draft, show or save Output 1 or Output 2 until (a) Pass 1, (b) Pass 2 and (c) the source trace below have ALL been completed.** Not for a long transcript, not for a first meeting, not for a re-run, not for a quick request, not because the call looks simple. If either read cannot be completed, say exactly what could not be read and stop - do not produce a partial report.

These rules exist because a decision made late in a call can silently change what an earlier part of the call said (e.g. a Tax-Free first set up for a child, then the client decides it should be in his own name for now), because garbled speech-to-text can be turned into a false fact, and because requests made in the closing minutes are the easiest to miss. Reporting the earlier state as final, inventing a fact, or missing a request are serious errors.

1. **PASS 1 - read EVERYTHING, in order, from the first line to the last.** Read the converted text in sequential chunks (about 400-450 lines each); never sample, skim, search-only or stop early. Confirm the last chunk reaches the closing "stopped transcription"/goodbye. Facts can sit anywhere, including filler chatter, a form being completed live, and the closing minutes. **A read done by another skill (e.g. `ff-population-transcript`) does NOT count as either pass** - this skill does both of its own reads.
2. **Keep a decision ledger while reading Pass 1** (internal working list, not saved): every decision, acceptance, refusal, "let me think", change of mind, correction of a name/figure/date, every new fact (owner, payer, beneficiary, product, amount, start date, address, bank, who does what, next appointment), **every request or instruction either person makes** (what Sitamah must send or ask, what the client must send, what goes in the what's-next email, offers Paul makes such as reviewing a spouse's portfolio, things put on hold), each with timestamp and speaker.
3. **PASS 2 - a second, separate, COMPLETE read.** After the Pass 1 ledger exists and BEFORE any output is written, read the ENTIRE transcript again from the first line to the last, in chunks, this time checking every ledger entry against the actual words and hunting for anything Pass 1 missed - especially the closing minutes, the client's questions, anything the client asks Paul/Sitamah to do, anything Paul offers, anything left "for now", and every figure and name. Correct or add ledger entries as needed. **A keyword scan does NOT count as a read, and neither does re-reading only the parts that look important.**
4. **The FINAL state governs.** If something is decided or changed later in the call, the later statement overrides the earlier one. Report the final state as the current position and record the earlier state as `Changed` (before -> after, and who decided). Never present a superseded state as current.
5. **Keyword scan (in addition to, never instead of, the two reads)** - search the transcript for decision and change words - `change`, `instead`, `rather`, `actually`, `for now`, `later`, `keep it`, `leave it`, `get back to you`, `in your name`, `his name`, `her name`, `owner`, `beneficiary`, `payer`, `address`, `spell`, `wrong`, `correct`, `sort that out`, `tomorrow`, `think about`, `go ahead`, `happy`, `not happy`, `agree`, `decline`, `cancel`, `increase`, `reduce`, `put it in`, `email`, `send`, `wife`/`husband`/`partner`, `credit life`, `retrench`, `instalment`/`installment`, `protector`, `cede`/`cession`/`ceded`, `payback`/`payout`, `bank`, `bond`, `card`, `waiting period`, `months`, `pays`/`covers`, `date`, `Monday`...`Friday`, amounts - and make sure every hit is reflected in the ledger and outputs.
6. **Resolve garbled words using context** from the Overview, quotes, Fact Find and earlier notes, then flag only what is still ambiguous. **A garbled line is NEVER turned into a fact.** Read the whole exchange around it; if it can mean opposite things (e.g. "I've got no, I've got a medical condition that I know of" can mean he HAS or has NO known condition), do not assert either reading - flag it to Paul as garbled and leave it out of the outputs (or, for a health or other sensitive item, ask Paul before writing anything). Digit-by-digit read-outs are never trusted from the transcript - they are checked against the live application (Step 2b, follow-up only) and never written into the outputs.
7. **SOURCE TRACE before drafting (the third gate):** for EVERY bullet in Output 1/Output 2 and EVERY action point, identify (internally) the transcript timestamp(s) it comes from, or the named document it comes from (Overview, quote, Fact Find Summary, earlier note, correspondence). **Anything with no source is deleted. Nothing is added because it "would make sense", "is usual", or "seems implied".** In particular: an action is only written if Paul said it, the client asked for it, or Paul clearly instructed it; "leave it for now / the client will get back to us" is NOT a chase action; an item the client declined or put on hold is reported as on hold, not as an open task for Sitamah.
8. **Cross-check the final state against hard evidence:** client replies in Outlook (Step 1c), the live applications (Step 2b, follow-up only), the quotes and the Overview.
9. **Coverage check before delivery:** walk the ledger entry by entry and confirm each one appears in Output 1 and/or Output 2 (every request/instruction in the ledger must map to a Sitamah action or a status line). Then do a **verification pass of the drafted outputs against the transcript**: any wrong person, wrong figure, wrong date, wrong status, contradiction, invented item, or action wrongly worded as conditional on another when the two are actually independent (per the rule in Accuracy below). For a meeting that includes an acceptance, a change of owner/beneficiary/payer, or money amounts, use an independent verification (a subagent where the Agent tool is available) to re-check the key facts against the transcript.
10. **Say it in the delivery message (one line):** "Transcript read in full TWICE (Pass 1 and Pass 2, N lines each)", the number of ledger decisions/changes, confirmation that every action was source-traced, and any change-of-mind items reported as `Changed`. **If this line cannot be truthfully written, the report must not be delivered.**

## Step 1c: Correspondence check - CURRENT transactions only (Paul's rule, 06/10/2026) - follow-up meetings only

Emails back and forth with the client and the providers are part of the evidence, so check them - but only the ones about the transactions in this advice cycle. Not applicable at a first/Fact Find meeting (no prior proposal emails exist yet).

1. **What to check (Outlook, via the Microsoft 365 tools):** (a) the client's replies to the proposal emails sent for the current quotes; (b) the provider/insurer quote emails for the current quotes and any email requesting or chasing a quote; (c) our own sent emails for these transactions, and any reply or acknowledgement; (d) anything sent or received since the previous meeting that concerns these products.
2. **What NOT to check:** historical correspondence from earlier years, unless Paul explicitly asks.
3. **Use it:** confirm acceptances (Step 4), confirm what was sent and when, spot anything outstanding and report it as Still open. Follow `outlook-emails-skill` tracking.
4. Never send an email from this skill. Where an email should be sent (e.g. a revised-quote request, Step 4b), prepare a DRAFT, show it to Paul and only send after his explicit yes.

## Step 2: Build the context pack (mandatory, every follow-up run; not applicable at a first/Fact Find meeting)

Inside the client's folder, read in this order (all PDFs; render pages as images if text extraction is empty):

1. `2. Fact Find\Fact Find Transcript - ... .pdf` and `Fact Find - ... .pdf` (the client's baseline).
2. The Fact Find Summary PDF.
3. **Every** earlier `Follow-Up Appointment Summary Notes - ... .pdf` (and any `WhatsApp Call Summary`), oldest to newest.
4. **The most recent** `1. Overview\2026\WR Overview - ... .pdf`.
5. **Quotes:** open `Comparative Quotes` in each transaction folder. Record insurer, type, CP/quote number, date and premium.
6. If something is missing, say so in one line and continue with what exists.

From this build two working lists (not saved anywhere):
- **Quote register:** every quote on file with insurer, type, number, premium, date.
- **Area ledger:** for each planning area, what was previously discussed, decided, requested and still outstanding. **At a first/Fact Find meeting, the area ledger is simply the Fact Find's own content, reorganised under the eight planning areas** - everything is `New` (nothing to carry forward yet).

## Step 2b: Read the applications (mandatory when applications exist; not applicable at a first/Fact Find meeting)

1. In every **current** transaction folder, list `Applications` and pick the real applications. List the folders on the client's own machine/OneDrive for the real state.
2. Stage them and read the filled field values. Note each file's last-modified date against the meeting date.
3. Compare each application against the transcript and against each other for shared details, and against the accepted quote and meeting date.
4. Applications are only ever compared and reported here; they are changed in Step 6 via `complete-applications-skill`.

## Step 3: The planning areas (structure of BOTH outputs)

Paul looks at eight areas. They appear under these headings, in this order:

1. **Risk Planning** - life, severe illness/dread disease, disability, income protection, retrenchment/instalment protectors.
2. **Retirement Planning** - RAs, pension/provident; **RGAR** is reported here.
3. **Investment Planning** - tax-free, endowments, unit trusts, savings; **EGAR** is reported here.
4. **Medical Aid**
5. **Will**
6. **Short-Term Insurance**
7. **Other** - debt, children, health, risk tolerance, general client information (only when something notable was said).

Show only areas that were discussed or still have something open; add one line for the rest. Never pad. **This structure applies to a first/Fact Find meeting's Planner note exactly as it applies to a follow-up's** - map the Fact Find's own content into these headings rather than any other grouping.

## Step 4: Quote rules

- When a quote is discussed, name it once: **insurer, quote type, CP/quote number, premium**. Match what was said on the call against the quote register and the Overview; if two quotes could fit, say which one and why, and flag it.
- Non-CP quotes: use the quote number printed on the quote; if none exists, state "no quote number on file". **At a first/Fact Find meeting a quote/FNA is often only just being requested, with no number yet** - say "requested" and name the insurer/product.
- **Do not report quotes line by line** - but a benefit specifically discussed must be explained in one short bullet (Step 4c).
- **Acceptance:**
  - **Risk policy:** verbal acceptance in the Teams call is the acceptance.
  - **RA / Investment / Tax-Free:** verbal confirmation AND a reply to the proposal email. Record `Verbally confirmed - awaiting email reply to proposal` until seen.
  - Anything the client wants to think about is `Pending - client deciding`, never accepted.
  - **At a first/Fact Find meeting, nothing has been quoted yet, so most items are simply `requested` / `still open`.**

## Step 4b: Owner / life assured / contracting party changed -> REVISED QUOTE (any insurer) - follow-up meetings only

Not applicable at a first/Fact Find meeting (no quote exists yet to revise).

1. **Detect it:** flag every accepted or pending product whose owner, life assured or contracting party now differs from the name on the quote.
2. **Ask the provider for a revised quote in the new name.** Applies to ANY insurer or product provider.
3. **Draft, don't send.** Show Paul the draft and send only after his explicit yes.
4. **Track it:** record `Revised quote requested from [provider] on [date] - awaiting` and follow `outlook-emails-skill` tracking.
5. **Report it:** `Changed: owner [old] -> [new]` plus the action `Sitamah to request / chase revised quote`.

## Step 4c: Quote literacy and cession rule (Paul's rule, 07/10/2026 - never miss a benefit that was explained on the call)

**At a first/Fact Find meeting there is usually no accepted quote yet to read** - this step applies once a quote exists; until then, note what was discussed as being requested/pending.

1. **Quote-literacy check.** For every product/benefit Paul explains, open the discussed quote in `Comparative Quotes` and read what it actually does: trigger, waiting period, months paid, conditions. Report it in ONE short plain-English bullet. If the quote does not state it, say "not stated in the quote" and flag it.
2. **Name the line items.** Name specific debts in words, never account numbers.
3. **Cession rule.** If a benefit needs ceding: (a) report in both outputs; (b) add the action `Sitamah to arrange for [the line items] to be ceded to [the bank] and send the cession documents to [client] to sign`; (c) check the application; (d) record `Still open` until the signed cession is back.
4. **Coverage check.** Every benefit Paul explained must map to a Step 4c bullet and a Sitamah action where cession/signature is needed.
5. **Be resourceful - look beyond the quote (Paul's rule, 07/10/2026).** Before flagging a detail as unknown, search: (a) the Fact Find Summary / Fact Find; (b) the latest WR Overview; (c) earlier Follow-Up Notes; (d) the applications; (e) current-transaction correspondence. Only if every source is silent or they conflict, flag it plainly.

## Step 4d: Credit life on a debt that new cover now protects (Paul's rule, 07/10/2026 - ALWAYS add it)

Must ALWAYS appear in the report, even if nobody mentioned it on the call - including at a first/Fact Find meeting where this is often first discovered.

1. **Find it (Step 4c item 5 - be resourceful).** For every debt the new cover protects, check the Fact Find Summary / Fact Find, the latest WR Overview, earlier notes, applications. Record per debt: lender, whether credit life exists, the monthly cost or `unconfirmed`.
2. **Report it** one short bullet per debt. Mark it `Still open`.
3. **Actions - all `Sitamah to ...`:** (a) get the credit-life details from the client; (b) ask the client what he wants to do; (c) cancel it ONLY after the new policy has been accepted and is in force.
4. **Never cancel early.**
5. If the client has no credit life on a debt, say so only when the Fact Find records it explicitly; do not invent one.

## Step 5: Carry-forward against earlier meetings (follow-up meetings only - a first/Fact Find meeting has nothing to carry forward)

Using the area ledger, tag each point: **Resolved**, **Still open**, **New** (everything at a first/Fact Find meeting is `New` or simply `requested`/`still open`), **Changed** (before -> after). Add a short "Since the last meeting" block at the top of Output 2. (Not applicable to a first/Fact Find meeting, which has no Output 2 of its own.)

## Step 6: Application differences and correction hand-off (follow-up meetings only; not applicable at a first/Fact Find meeting)

Using Step 2b, build the **application differences** list:
- **Differs from the meeting**, **Missing**, **Not yet captured**, **Wrong reference**.

Report it in both outputs: one short bullet per application naming the application and WHAT differs in words. Never write ID numbers, account numbers or tax numbers.

Then **call `complete-applications-skill` automatically after the report** (Correction / Sync mode, its Step 7). The source of any detail to carry across is ONLY a current application in a current transaction folder, never an older one unless Paul explicitly says so. **If anything is unclear, ask Paul BEFORE any change is made.** Corrections are made in place. If no applications exist for the client, skip Step 2b and Step 6.

## Accuracy (both outputs, always)

- No fact, figure, name or instruction may be dropped or guessed. Headline figure per topic only, but exact. Do not editorialise or add advice that was not discussed.
- **Be resourceful before you ask or flag:** a detail missing from one document is almost always in another - check the quote, then the Fact Find Summary / Fact Find, the latest WR Overview, earlier Follow-Up Notes, the applications and current correspondence before writing "to confirm" or handing a lookup to Sitamah or Paul.
- **Resolve before you flag:** use the Overview, quotes, Fact Find and earlier notes to resolve garbled figures and names. Flag only what is still genuinely ambiguous.
- **ALL ACTION POINTS GO TO SITAMAH (Paul's rule, 06/10/2026).** Every action in Output 1 and Output 2 is assigned to **Sitamah** - what's-next emails, FICA requests, meeting invites, application updates/chasing, emailing any provider, requesting or chasing quotes, sending documents, diarising follow-ups. Even if the transcript has Paul saying "I'll email"/"I'll send", write it as `Sitamah to ...`. Paul is never listed as the owner of an action point. Insurer/provider contacts appear as the party being contacted, not as invented owners. **This rule applies identically at a first/Fact Find meeting.**
- **Two genuinely independent Sitamah actions are never worded as one waiting on the other, unless the transcript or Paul actually said they depend on each other.** A request to an insurer/provider and a separate request to the client for a supporting document are usually independent - write them as two parallel bullets ("Sitamah to request X from [provider] now" / "Sitamah to separately request Y from the client"), not as "request X once Y is received" or "X, pending Y", unless the call or Paul specifically established that dependency. **Named precedent:** [client B], 07.10.26 (review) - a first draft wrote the BrightRock Servicing FNA request as "pending the updated psychiatric report", implying Sitamah must wait for the report before requesting the FNA from BrightRock. Paul corrected this: the FNA is requested from Lizelle Cachado now, with the Fact Find's changes and all the same loadings, independently of the separate request to the client for the report - the two run in parallel.
- **NO INFERENCE (Paul's rule, 08/10/2026).** Record what was SAID, not what seems likely, usual or implied. Never invent a fact about the client (above all health, family, money or legal facts) and never invent an action. Every statement must pass the Step 1b source trace. When the transcript is garbled and two readings are possible, flag it to Paul instead of choosing a reading.
