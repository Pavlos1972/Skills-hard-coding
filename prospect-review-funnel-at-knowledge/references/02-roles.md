## Roles and the stage pattern

- **One owner per checklist (Decision 37, Paul 30 Oct):** there can NEVER be a mixture of PK and SR lines in one checklist (CL lines exempt); check every new or changed checklist before writing it.
- **SR** = Sitamah (admin, documents, quotes, invites, submissions, audits). **PK** = Paul (calls, meetings, approvals, advice, decisions). **CL** = Claude (transcripts, FF Summary, Astute Summary, comparison skills, G6 notes summary).
- Every stage ends with "Update Task Notes for this stage" and an AUTOMATION **hand-over line** (Paul, 4 Nov): the owner MOVES THE TASK to the next stage's column on the board, so the next owner (SR ↔ PK) sees it and no Task gets lost — e.g. Sitamah finishes G1 and moves the Task to G2, where Paul is responsible. It is done by hand (the owner moves the card; Claude never drags cards); in AT, ticking the line Done also opens the next stage's module. The stage names are Section / board-column names, NOT Client Status values (Client Status has 10 fixed values: Active, Active - Not Verified, Deceased, Director / Shareholder / Trustee, EB Member, Family Member, NTU, Other, Prospect, Terminated). **Built in AT 4 Nov (D55):** the lines read "MOVE THE TASK TO COLUMN <stage> → <next owner>" (61 renamed, 20 added where a stage had none, e.g. parents G3, G5, G6; Review G4, G5). Only the end-state lines that set Active or NTU change the real Client Status. **Never describe these lines as a Client Status change.**
- Item types: action; "— Received"; value placeholder (DOC:, COC:, Teams Appt …); conditional sub-block (Life Cover only, Servicing, Replacement case → Skip when not applicable); informational outcome (G2 LOA happy / not happy, not a branch); **decision outcome** (bold heading, one chosen, others skipped); **GATE** (hard stop, not a branch); audit item.
